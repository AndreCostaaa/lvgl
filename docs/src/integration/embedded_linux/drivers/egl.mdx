## Overview

**EGL** (Embedded-System Graphics Library) is the platform layer that binds OpenGL ES to a native windowing
system. It sits lower than GLFW and is more closely tied to the platform's own drivers, which is why it is
the path LVGL uses for GPU rendering on embedded Linux.

You rarely enable EGL on its own. It underpins the hardware-accelerated backends of the other drivers:

- [DRM](/integration/embedded_linux/drivers/drm) with `LV_LINUX_DRM_BACKEND_EGL`
- [Wayland](/integration/embedded_linux/drivers/wayland) with `LV_WAYLAND_BACKEND_EGL`
- [SDL](/integration/pc/sdl) with `LV_SDL_BACKEND_EGL`

Selecting any of those backends turns EGL on for you and sets up the context during normal driver
initialization — there is nothing extra to call. Beyond that, EGL offers two things the other drivers do
not: a standalone window path for platforms LVGL does not otherwise cover, and off-screen rendering with no
display server at all.

## Configuration

<ApiLink name="LV_USE_EGL" /> enables the EGL layer.

<Callout type="info" title="Not selectable in menuconfig">
<ApiLink name="LV_USE_EGL" /> has no Kconfig prompt — it is a derived symbol. Normally a driver backend
selects it for you. To turn it on directly, use a compiler definition (`-DLV_USE_EGL=1`) or set it in your
configuration header.
</Callout>

Two consequences worth knowing:

- **Nothing to link.** LVGL loads `libEGL.so` and `libGLESv2.so` at runtime with `dlopen`, so EGL does not
  appear among the build dependencies and no `-lEGL` is needed. The libraries must be present on the target
  at run time, not at link time.
- **EGL does not imply OpenGL ES.** <ApiLink name="LV_USE_EGL" /> and <ApiLink name="LV_USE_OPENGLES" /> are
  separate symbols. Any use of EGL to drive a display needs both.

<Callout type="warning" title="EGL and GLFW are mutually exclusive">
<ApiLink name="LV_USE_GLFW" /> cannot be combined with <ApiLink name="LV_USE_EGL" />; each wants to own
context creation. Pick one.
</Callout>

## Usage

With a driver backend, EGL is invisible: configure the driver as its own page describes and it initializes
EGL during setup. See [DRM](/integration/embedded_linux/drivers/drm) or
[Wayland](/integration/embedded_linux/drivers/wayland) for working examples.

For custom platform integration, `lv_opengles_egl_window_create` creates an
<ApiLink name="lv_opengles_window_t" /> usable with the same generic LVGL OpenGL APIs as a GLFW window,
letting you drive LVGL through your own context management.

<Callout type="warn">
The standalone window API is private and experimental. Expect breaking changes.
</Callout>

## Off-Screen Rendering Without a Display Server

<Callout type="warn">
This feature is experimental. Expect breaking changes.
</Callout>

<ApiLink name="lv_opengles_pbuffer_create" /> creates a display that renders on the GPU with no window
system at all, and reads the finished frame back into the display's draw buffer. It creates its own EGL
context on an off-screen surface, so it needs neither a display server nor an existing OpenGL context.

### When This Is the Right Tool

The pbuffer display earns its place when you need the **GPU renderer's** output on a machine with no
display. Concretely:

- **Rendering 3D content headless.** The software renderer cannot draw glTF at all, since
  `LV_DRAW_HAS_3D_SUPPORT` comes from the GL renderers. Generating a thumbnail of a
  [glTF](/libs/gltf) model on a server, or regression-testing 3D content in CI, has no
  software-rendered equivalent.
- **Screenshot testing a GPU-rendered UI.** If your product renders with NanoVG, software-rendered
  screenshots will not match what the device produces. LVGL's own test suite uses this display for
  exactly that reason.
- **Batch or server-side image generation** — report pages, print previews, thumbnails — where you want
  GPU rendering but there is no screen.

### When to Use Something Else

- **You already have an OpenGL context** (embedding LVGL in a game or other GL application): use
  <ApiLink name="lv_opengles_texture_create" /> instead. It hands you a texture ID with no readback and
  no context creation. See [OpenGL Driver](/integration/embedded_linux/drivers/opengl_driver).
- **You only need headless *software* rendering:** you need none of this. The software renderer is
  already headless — just give a display a buffer and never present it.
- **An interactive or high-frame-rate output path:** reading pixels back synchronizes with the GPU every
  frame, which throttles throughput. This is a capture path, not a display path.

### Configuration

Requires EGL, the OpenGL ES driver and the NanoVG draw unit: <ApiLink name="LV_USE_EGL" />,
<ApiLink name="LV_USE_OPENGLES" /> and <ApiLink name="LV_USE_DRAW_NANOVG" />. Remember that
<ApiLink name="LV_USE_EGL" /> is not selectable in menuconfig — set it with a compiler definition or in your
configuration header.

### Basic Usage

```c
#include "lvgl/lvgl.h"

#define WIDTH  800
#define HEIGHT 480

int main(void)
{
    lv_init();
    /* Don't forget the tick callback */

    lv_display_t * disp = lv_opengles_pbuffer_create(WIDTH, HEIGHT);
    if(disp == NULL) return 1;

    /* An OpenGL ES 3 context is requested first, falling back to ES 2. glTF needs ES 3. */
    if(lv_opengles_pbuffer_get_gles_version(disp) < 3) {
        LV_LOG_WARN("No OpenGL ES 3 context, 3D content is unavailable");
    }

    lv_demo_widgets();

    /* Render one frame. The flush reads the GPU result into the display's draw buffer. */
    lv_timer_handler();

    /* The rendered pixels, as XRGB8888 */
    lv_draw_buf_t * frame = lv_display_get_buf_active(disp);
    /* ... encode `frame`, hand it to a video pipeline, compare it against a reference ... */

    /* Take the handle before lv_deinit(), then release the GL context afterwards.
     * Draw units still issue GL calls while they are being destroyed, and lv_deinit()
     * deletes displays before draw units. */
    lv_opengles_pbuffer_t * pbuffer = lv_opengles_pbuffer_get_handle(disp);
    lv_deinit();
    lv_opengles_pbuffer_destroy(pbuffer);

    return 0;
}
```

Use <ApiLink name="lv_opengles_pbuffer_read_to_draw_buf" /> if you want an additional copy of the frame
in a draw buffer of your own rather than reading the display's.

### Known Limitations

- Only the NanoVG draw unit is supported. It renders through the bound GL framebuffer, which is what the
  readback expects. <ApiLink name="LV_USE_DRAW_OPENGLES" /> renders into the display's own texture, which
  would additionally have to be composited before the readback; that path is not implemented.
- The resolution and color format are fixed when the display is created. Changing either afterwards is
  not supported.
- No hardware multisampling. The color attachment is single-sampled, so antialiasing comes from NanoVG's
  own geometry AA. Rendering into a multisampled off-screen surface instead is not portable — Mesa rejects
  reading pixels back from one.
- Requires an EGL platform that offers off-screen configs, such as `EGL_MESA_platform_surfaceless`. The
  driver falls back to the default EGL display if that platform is unavailable.

## Support

| Capability | Via a driver backend | Off-screen pbuffer |
|---|---|---|
| Rotation | Hardware (GPU) | Hardware (GPU) |
| Runtime resolution change | Depends on the driver — see its page | No — fixed at creation |
| Runtime color format change | No | No — fixed at creation |
| Color formats | Set by the driver | XRGB8888 |
| Multiple displays / windows | Set by the driver | Yes |
| Hardware acceleration | OpenGL ES | OpenGL ES, NanoVG only |
| Render mode | Set by the driver — fixed | Full — fixed |
| Input | Set by the driver | None — there is no window |
