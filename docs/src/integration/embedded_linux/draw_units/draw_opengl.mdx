## Overview

The OpenGL ES draw unit renders widgets in software, caches the result as an OpenGL texture, and composites
those textures on the GPU. Whenever a later frame asks for something already in the cache, the texture is
reused instead of redrawn — which is most of the screen, most of the time, in a typical UI.

That makes it fast for static and slowly-changing content, and no faster than software rendering for content
that changes every frame.

<Callout type="info" title="Prefer NanoVG">
[NanoVG](/integration/embedded_linux/draw_units/draw_nanovg) is the recommended GPU renderer on Linux: it
performs better and supports more LVGL features. Reach for this draw unit when you specifically want the
texture cache, or when NanoVG's limitations do not suit you.
</Callout>

### Requirements

- OpenGL ES 2.0 or newer
- An OpenGL context, created by one of the display drivers listed in
  [OpenGL Overview](/integration/embedded_linux/opengl) or by your own code

## Configuration

Enable <ApiLink name="LV_USE_DRAW_OPENGLES" />. It turns on <ApiLink name="LV_USE_OPENGLES" /> and the 3D
capability flag for you.

### Options

| Symbol | Default | Meaning |
|---|---|---|
| `LV_DRAW_OPENGLES_TEXTURE_CACHE_COUNT` | `64` | Number of textures kept in the cache. More entries mean fewer redraws but more GPU memory. |

## Limitations

- **No gain without cache hits.** Performance is the same or slightly worse when drawn areas are never found
  in the cache — widgets whose color or shape changes every frame. The "Multiple labels" scene of the
  benchmark demo, which recolors a label randomly each frame, is the worst case.
- **Layer transparency.** Layers that have both transparent pixels and an overall layer opacity do not blend
  correctly. Visible in the border corners of the benchmark demo's "Containers with opa_layer" scene.
- **No layer rotation.** Rotated layers are unsupported. Rotated *images* are fine.

[NanoVG](/integration/embedded_linux/draw_units/draw_nanovg) has none of these limitations.

## Support

Render mode and buffering are not configurable per draw unit — they are fixed by whichever display driver
owns the buffers. See that driver's page: [DRM](/integration/embedded_linux/drivers/drm),
[Wayland](/integration/embedded_linux/drivers/wayland),
[GLFW](/integration/embedded_linux/drivers/glfw) or [SDL](/integration/pc/sdl).

Note that enabling this draw unit changes how some drivers set up their buffers — the GLFW driver switches its
window displays to the full render mode, for instance — and that the off-screen
[EGL pbuffer display](/integration/embedded_linux/drivers/egl) does **not** support this draw unit, only
NanoVG.
